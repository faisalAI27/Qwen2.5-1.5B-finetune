# Implementation decisions

## 2026-11-14: Stage 1

- Use the existing project root, preserving the proposal and roadmap. Initialize local Git without making a commit or publishing anything.
- Use simple Python modules under `src/s1small` and standard-library `unittest`. Stage 1 needs no ML runtime dependencies.
- Create an isolated `.venv` for the project shell and tests. Inspect the existing global ML installation separately; do not copy its full stack into the venv or claim it is a validated training recipe.
- Resolve source revisions using GitHub/Hub metadata, without downloading weights or dataset rows. Store pins in `configs/sources.json`.
- Use only the local M1 Mac per user instruction. PyTorch MPS is the first backend candidate; MLX quantized LoRA remains an untested alternative. Neither training feasibility nor final precision is decided.
- Keep the benchmark sealed. Develop extraction/grading on synthetic and development examples before freezing evaluation, even if the roadmap discusses it primarily in Stage 8.
- Save hardware and dependency observations as JSON. An uninitialized repository has a null commit; missing ML packages are valid, explicit states. Never report MPS's working-set recommendation as dedicated VRAM.

## 2026-11-14: Stage 2

- Select seed 42 and deterministic SHA-256 ranking for the immutable original 900/100 split. Save full-row checksums, original source row indices, question digests and source revisions. Reject changed outputs and normalized duplicate questions crossing partitions. The one duplicated question pair is entirely in training; retain both original examples and disclose it.
- Download only pinned s1K and tokenizer assets. The pinned MATH-500 source is JSONL rather than columnar: stream it, project immediately to question/ID records and discard all other fields without logging or persisting them. This is a documented transport deviation from the roadmap's question-only download wording; no benchmark answers/scores guide decisions.
- Run exhaustive lexical overlap screening at similarity >=0.80 on at least eight tokens; manually inspect candidate question pairs. Exclude two identical questions, one formatting-only duplicate and one task with the same complex recurrence/initial condition but a different requested representation. The conservative last exclusion prevents shared-solution leakage. No model outputs or test scores were used.
- Preserve the raw split, apply exclusions in a separate immutable eligibility manifest, and do not refill partitions. Result: 896 eligible train, 100 development, 996 eventual final-training rows before any context exclusions. Use this eligibility manifest downstream. Exclusion reasons and benchmark IDs are recorded in `configs/data_exclusions.json`; benchmark questions themselves remain all 500.
- Construct the released s1 text now because accurate length measurement requires it; this does not complete Stage 4 label/masking validation. Use the exact pinned 1.5B tokenizer, no truncation and a single full-sequence offset mapping so counts add up. Boundary-spanning tokens count as structure for this audit, not as a prescribed training loss mask.
- Measure candidate context coverage without selecting a training maximum yet. Only 39 original examples fit at 2,048 tokens, 127 at 4,096, and 988 at 8,192; the full maximum is 9,109. Do not silently discard most of the data to make a pilot easy. Test full examples of increasing lengths in the later memory pilot.
- Validate the tokenizer/data workflow in the isolated venv and record `requirements-data-lock.txt`. Torch/PEFT/MLX are deliberately absent there; the data lock is not evidence that a training stack is installed or compatible. The existing global packages were used for initial acquisition/audit while dependency downloads completed, followed by an isolated offline replay with identical manifests and length outputs.

Record the relevant 36-distribution runtime closure. Unrelated inherited global dependency conflicts are documented; the relevant closure passes its own requirement checks.
- A small native MPS FP16 SDPA probe passed under strict deterministic algorithms. Actual model inference remains pending. Queue a short development-only test before five-question A/B repetitions and a fresh-load comparison; stop on failure.
- The user asked to continue and complete the work, and the roadmap is guidance. While waiting on the checkpoint, perform independent Stage 4 CPU/tokenizer validation rather than treating the stage order as a reason to idle. All 996 eligible examples passed prompt-boundary, complete-target, end-token and padding checks; 52 tests passed. The full decoded sample was inspected. See `docs/training_format_audit.md`.
- Keep the released teacher `attempt` even where its mathematics is not validated. A format check is not a quality label. Use no benchmark scores for filtering or settings, and select the eventual development metric with proof/mixed-task examples in mind.
- Preserve the no-truncation policy and leave the training context ceiling unset until measured memory profiling. No fine-tuning or benchmark evaluation has run.
- The user's repeated instruction to continue and complete the project supersedes the roadmap's routine stop-for-review wording. Proceed through remaining acceptance gates without seeking another go-ahead for already authorized work. Preserve genuine scientific/feasibility gates and measured evidence; do not turn network waits or passing unit tests into claims of completed experiments.
- The LoRA preflight inspected the pinned architecture using meta tensors, not pretrained weights: 28 layers, 112 q/k/v/o projection targets and 4,358,144 FP32 adapter parameters, with base parameters frozen. PEFT 0.21.3 imported and attached the declared rank-16/alpha-32 adapter successfully in this architecture-only check.
- Native tiny BF16 linear/attention forward-backward probes returned finite gradients. Use BF16 for the first training pilot, while retaining FP16 baseline inference. The initial FP16 toy AMP test used fully FP16 trainable parameters and was rejected by GradScaler's dtype rule; the corrected FP32-parameter/autocast-FP16 test passed. This was a test-pattern issue, not evidence of unsupported MPS AMP.
- Prepare a one-example backward profile before any 20-row pilot. The technical pilot uses the shortest 20 eligible training examples, micro-batch 1 and accumulation 4 (five updates), with complete targets and no context exclusions. These are technical-smoke settings rather than a final recipe; profile longer complete examples separately. Record finite gradients, sampled MPS memory, input/supervised throughput and exact adapter fingerprints plus generation before/after clean reload.
- A later test invocation exposed macOS hidden flags on the editable `.pth` links. Python 3.13 intentionally skips hidden links. `scripts/fix_editable_install.py` clears only the hidden flag on this project's source-only link inside its venv; it does not alter global packages or other flags. Re-running the test suite passed 55 tests. CLI workflow scripts already insert the repository source path directly.

## 2026-11-14: Stages 3–4 accepted; measured Stage 5 failures

- The complete checkpoint passed its upstream checksum. All 28 actual native MPS baseline generations completed; the 10 main A/B repeat pairs and all four cross-load comparisons matched token IDs. The reasoning outputs are explicitly marked unfinished at their provisional cap. No accuracy score was calculated; see `stage3_report.md`.
- Complete-example formatting and assistant-only masking passed for every eligible row. Keep the no-truncation policy for feasibility profiles; a technical pilot on short examples does not justify excluding long rows.
- The first standard BF16 training profile exhausted the memory allowance at the 151,936-way vocabulary cross entropy on the shortest complete example. Retain the memory cap and failure log. Instead of changing the dataset, checkpoint small output-head/loss chunks, recomputing them during backward. The objective remains the mean over precisely the same shifted, supervised targets. Tests compare dense/chunked loss and adapter gradients, including actual tiny Qwen2 LoRA with decoder checkpointing and nonzero A/B matrices.
- The first chunked pretrained-model profile fit the memory cap but failed gradient validation. Do not start optimizer updates until the numerical/gradient issue is diagnosed and corrected. Log every failed configuration rather than relabeling it successful.
- Hidden flags on editable links recurred. Use explicit `PYTHONPATH=src` for reproducible test invocation; CLI scripts already resolve the source directory. This import-path problem is separate from the recorded model failures.
- Standard eager attention passed at 712 tokens but exhausted memory during backward at 2,006 tokens. Register a query-chunked eager implementation with the original masks, scaling, all keys/values and FP32 softmax. Checkpoint chunks during backward. CPU output/gradient comparisons and an actual complete 2,006-token MPS backward pass succeeded; no context exclusions were introduced.
- The first 20-row pilot stopped before updating because its MPS norm reduction was nonfinite despite finite gradient elements. Use a CPU float64 global norm for the small adapter gradients, with the ordinary norm-1 clipping rule; keep every failed run. A real-head-geometry random Qwen CPU/MPS gradient comparison passed for FP32 and BF16, including nested checkpointing. The second pilot records every microbatch and verifies finite adapter parameters after each optimizer step. Large pretrained-model gradient norms and the scope of the numerical probe are disclosed in `hardware_pilot.md`; no final-training or accuracy claim follows from these checks.
